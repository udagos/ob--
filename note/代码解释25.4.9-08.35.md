


这段汇编代码是 ARM 架构的启动代码，主要功能是**初始化内存管理单元 (MMU) 和设置缓存 (Cache)**。它通常用于在嵌入式 Linux 或其他需要虚拟内存的 ARM 系统启动的早期阶段。让我们逐步分析这段代码：

**1. `.globl MMUTable` 和 `.section .mmu_tbl,"a"`**

*   `.globl MMUTable`:  声明 `MMUTable` 为全局符号，这意味着这个符号可以在其他汇编或 C 代码文件中被引用。
*   `.section .mmu_tbl,"a"`:  定义了一个名为 `.mmu_tbl` 的段 (section)。  `"a"` 标志通常表示 "allocate"，意味着链接器会为这个段分配内存空间。  这个段用于存放 MMU 的页表数据。

**2. `MMUTable:` 标签 和 `.rept` 循环 -  构建 MMU 页表**

*   `MMUTable:`:  这是一个标签，标识了 MMU 页表的开始地址。
*   ==`.rept 0x0400` ... `.endr`:  `.rept` 是一个汇编宏指令，用于重复代码块指定的次数。这里 `0x0400` (1024) 表示循环 1024 次。==
*   `.word SECT + 0x15de6`  (以及后续类似的 `.word` 指令):  `.word` 指令用于定义一个 32-bit 的字 (word) 数据。. 在 ==MMU 页表中，每个条目通常是一个 32-bit 的描述符，用于定义 1MB 的内存区域的属性==。
    *   `SECT`:  这是一个变量，使用 ==`.set SECT, 0` 初始化为 0==， 并==在每次循环后使用 `.set SECT, SECT+0x100000` 递增 0x100000 (1MB)。== `SECT` 的值会随着循环迭代而增加，代表了当前页表条目映射的内存区域的 **基地址** (实际上是虚拟地址的高位部分，因为这里是 Section Descriptor).
    *   `0x15de6`, `0xc02`, `0xc06`, `0xc0e`, `0xc0a`, `0x4c0e`, `0x0`: 这些十六进制数值是 ==**MMU Section Descriptor 的属性编码**。  它们定义了对应 1MB 内存区域的权限、缓存策略等==。  让我们更详细地分析一些例子：

    **解码 MMU Section Descriptor 示例 (以 `.word SECT + 0x15de6` 为例，对应 DDR Cacheable 区域)**
	==指令 `.word SECT + 0x15de6` 是用来**创建一个 32-bit 字 (word) 数据，并将其作为 MMU (内存管理单元) 页表中的一个条目**。更具体地说，它定义了一个 **Section Descriptor**，用于描述一个 1MB 的内存区域的属性。==
    *   `0x15de6`  (二进制: `0b 0001 0101 1101 1110 0110`)  需要参考 ARM 架构手册来解码 Section Descriptor 的位域含义。  通常，==Section Descriptor 的结构如下== (简化版本，具体细节请查阅 ARM Architecture Reference Manual):

        ```
        Bits [31:20] : Section base address (高 12 位， 加上 SECT 完成 32 位地址，但其实只用高位)
        Bits [19:18] : TEX (Texture bits) - Cache type control
        Bits [17:16] : AP (Access Permission) - 读写权限控制
        Bits [15:12] : Domain  - 访问域
        Bit  [11]    : S (Shareable) -  多处理器共享属性
        Bit  [10]    : C (Cacheable) - 是否允许缓存 (通常指 Data Cache)
        Bit  [9]     : B (Bufferable) - 是否允许写缓冲 (Write Buffer)
        Bits [8: 5]  : Reserved
        Bits [4: 0]  : Type/B,  bits [4:1] are type field, bit [0] is B=0
        ```

        *   **==`0x15de6` 解码== (根据注释 `S=b1 TEX=b101 AP=b11, Domain=b1111, C=b0, B=b1`)**:
            *   **S=1 (Bit 11):** Shareable -  表示该内存区域可以被多个处理器核心共享访问。
            *   **TEX=b101 (Bits 19:18):**  Texture = 5. 具体含义取决于 ARM 架构版本和实现，但 `b101` 通常与 **缓存策略** 相关，可能表示 Write-Back, Write-Allocate (WBWA) 类型的缓存 (需要查阅具体 ARM 架构文档确认)。
            *   **AP=b11 (Bits 17:16):** Access Permission = 3. 通常表示 **Full Access (读写权限)** - 允许特权模式和用户模式访问。
            *   **Domain=b1111 (Bits 15:12):** Domain = 15.  通常表示 **Domain 15**。  Domain 用于更细粒度的访问控制 (通常在更复杂的系统中使用，这里 Domain 15 可能作为默认或管理域)。
            *   **C=b0 (Bit 10):**  Not Cacheable (Non-cacheable Data).  **与注释 `(DDR Cacheable)`  矛盾!  代码和注释可能不一致。 `C=0` 通常表示禁止数据缓存。**
            *   **B=b1 (Bit 9):** Bufferable (Write-Buffer enabled).  允许使用写缓冲器，可以提高写性能。
            *   **结合注释 `(DDR Cacheable)` 但实际 `C=b0 (Not Cacheable)`，这里可能存在笔误，代码可能才是实际配置。 实际代码配置的是 Non-Cacheable 数据区域 (即使注释写的是 Cacheable)**。

        *   ==**`0xc02` 解码== (FPGA slave 区域, `S=b0 TEX=b000 AP=b11, Domain=b0, C=b0, B=b1`)**:
            *   **S=0 (Bit 11):** Not Shareable
            *   **TEX=b000 (Bits 19:18):** Texture = 0. 通常表示 Normal memory, Non-cacheable, Non-bufferable (需要查阅文档)。但在结合 C 和 B 位之后，实际缓存行为可能有所不同。
            *   **AP=b11 (Bits 17:16):** Full Access
            *   **Domain=b0 (Bits 15:12):** Domain 0
            *   **C=b0 (Bit 10):** Not Cacheable (Data)
            *   **B=b1 (Bit 9):** Bufferable
            *   **结论:  Non-cacheable but Write-Bufferable (通常用于外设寄存器映射区域).**

        *   ==**`0xc06` 解码== (Memory mapped devices, AMBA APB Peripherals, NOR, `S=b0 TEX=b000 AP=b11, Domain=b0, C=b0, B=b1`)**:  与 `0xc02` 属性相同，也是 Non-cacheable, Write-Bufferable.

        *   **==`0xc0e` 解码== (SRAM, `S=b0 TEX=b000 AP=b11, Domain=b0, C=b1, B=b1`)**:
            *   **C=b1 (Bit 10):** Cacheable (Data).  与之前的 Non-cacheable 区域不同，SRAM 被配置为 **可缓存的**。

        *   **==`0xc0a` 解码== (Linear QSPI - XIP, `S=b0 TEX=b000 AP=b11, Domain=b0, C=b1, B=b1`)**:  也是 Cacheable.

        *   **==`0` 解码== (unassigned/reserved regions, `S=b0 TEX=b000 AP=b00, Domain=b0, C=b0, B=b0`)**:
            *   **AP=b00 (Bits 17:16):** No Access.  禁止任何访问，访问这些区域会产生 **Translation Fault (MMU 异常)**，符合注释 `Generates a translation fault if accessed`.  这是为了保护未使用的内存区域。

        *   **==`0x4c0e` 解码== (OCM when mapped to high address - inner-cacheable,  `S=b0 TEX=b100 AP=b11, Domain=b0, C=b1, B=b1`)**:
            *   **TEX=b100 (Bits 19:18):** Texture = 4.  可能表示 Inner Cacheable (需要查阅架构文档). 这里注释也写了 `inner-cacheable`.
            *   **其他属性 (AP, Domain, C, B) 与 `0xc0e` 类似.**

*   `.set SECT, SECT+0x100000`: 在每次 `.rept` 循环结束后， `SECT` 的值增加 0x100000 (1MB)，这样下一个 `.rept` 循环生成的页表条目将映射到下一个 1MB 的内存区域。

**总而言之，`.section .mmu_tbl,"a"` 和 `.rept ... .word ... .endr` 块的作用是：**

1.  **定义一个 ==16KB 的 MMU 页表 `MMUTable` (4096 entries * 4 bytes/entry).==**, ==4096个条目==
2.  **使用循环和 `.word` 指令，填充页表条目，==每个条目定义了 1MB 内存区域==的 MMU 属性 (权限, 缓存策略等).**
3.  **==页表定义了以下内存区域的映射和属性== (根据注释和代码分析):**
    *   `0x00000000 - 0x3fffffff` (1GB): DDR (注释说是 Cacheable, **但实际代码配置可能是 Non-Cacheable Data, Write-Bufferable, 共享的**)。  **注意代码与注释的潜在矛盾点。**
    *   `0x40000000 - 0x7fffffff` (1GB): FPGA slave0 (Non-Cacheable Data, Write-Bufferable, 非共享,  Domain 0, Full Access)
    *   `0x80000000 - 0xbfffffff` (1GB): FPGA slave1 (同 FPGA slave0)
    *   `0xc0000000 - 0xdfffffff` (512MB): Unassigned/reserved (No Access - Translation Fault if accessed)
    *   `0xe0000000 - 0xe1ffffff` (32MB): Memory mapped devices (UART/USB/IIC/SPI/CAN/GEM/GPIO/QSPI/SD/NAND) (Non-Cacheable Data, Write-Bufferable, 非共享, Domain 0, Full Access)
    *   `0xe2000000 - 0xe3ffffff` (32MB): NOR (同 Memory mapped devices)
    *   `0xe4000000 - 0xe5ffffff` (32MB): SRAM (Cacheable Data, Write-Bufferable, 非共享, Domain 0, Full Access)
    *   `0xe6000000 - 0xf7ffffff` (320MB): Unassigned/reserved (No Access - Translation Fault if accessed)
    *   `0xf8000000 - 0xf8ffffff` (16MB): AMBA APB Peripherals (同 Memory mapped devices)
    *   `0xf9000000 - 0xfbffffff` (48MB): Unassigned/reserved (No Access - Translation Fault if accessed)
    *   `0xfc000000 - 0xffefffff` (768MB - 256KB): Linear QSPI - XIP (Cacheable Data, Write-Bufferable, 非共享, Domain 0, Full Access)
    *   `0xfff00000 - 0xffffffff` (1MB - 256KB):  OCM (inner-cacheable) (Inner-Cacheable Data, Write-Bufferable, 非共享, Domain 0, Full Access)

**3.  boot. s `.globl MMUTable`, `.global _boot`, ...  `.end` -  启动代码段 `.boot`**

*   `.globl MMUTable`, `.global _boot`, ... , `.global _vector_table`:  声明多个全局符号，包括 MMU 表, 启动入口点, 栈地址, 中断向量表地址等。
*   `.set TblBase , MMUTable`,  `.set Abort_stack, __abort_stack`, ... , `.set vector_base, _vector_table`:  使用 `.set` 指令定义了一些符号常量，将更具描述性的名称 (如 `TblBase`, `Abort_stack`) 与标签或符号 (如 `MMUTable`, `__abort_stack`) 关联起来，提高代码可读性。 这些 `__..._stack` 和 `_vector_table` 符号通常在链接脚本中定义，用于指定栈和向量表的内存位置。
*   `.section .boot,"ax"`:   定义启动代码段 `.boot`， `"ax"` 标志通常表示 "allocate" 和 "execute"，表明这段代码会被加载到内存并执行。
*   `_boot:`:  启动代码的入口点标签。

### **启动代码 `_boot:` 流程分析**

1.  **设置向量表基地址 (VBAR):**
    *   `mrc p15, 0, r0, c1, c0, 0`:  读取 CP15 协处理器的寄存器 1 (SCTRL - System Control Register) 到寄存器 `r0`。
    *   `bic r0, #0x2000`:  清除 `r0` 中的第 13 位 (V 位)。  ==**V 位为 0 时**，**向量表的基地址由 VBAR 寄存器 (Vector Base Address Register, CP15 寄存器 c12) 决定**==；V 位为 1 时，向量表基地址固定为 0xFFFF0000 或 0x0 (取决于架构配置，但Zynq-7000 通常配置为V=0情况下由VBAR决定基地址)。
    *   `mcr p15, 0, r0, c1, c0, 0`:  将修改后的 `r0` 写回 CP15 寄存器 1 (SCTRL)。
    *   `ldr r0, =vector_base`:  加载 `vector_base` 符号 (即 `_vector_table` 的地址，链接器在链接时会替换为实际地址) 到寄存器 `r0`。
    *   `mcr p15, 0, r0, c12, c0, 0`:  ==**将 `r0` 中的向量表基地址写入 CP15 寄存器 12 (VBAR)。**  **这样就设置了异常向量表的起始地址==。**

2.  **禁用 MMU (如果已启用):**
    *   `mrc p15, 0, r0, c1, c0, 0`: 读取 CP15 寄存器 1 (SCTRL) 到 `r0`.
    *   `bic r0, r0, #0x1`:  清除 `r0` 的第 0 位 (M 位 - MMU Enable bit)。
    *   `mcr p15, 0, r0, c1, c0, 0`:  将修改后的 `r0` 写回 CP15 寄存器 1 (SCTRL)。 **确保 MMU 在配置页表之前被禁用。**

3.  **手动映射虚拟地址 0x20000000 到 0x00000000 (Non-Cacheable):**
    *   `ldr r3, =0x1ff`:  加载循环计数器 `r3` 为 0x1ff (511， 加 1 是 512).  这个循环将设置 ==512 个 MMU 条目，==覆盖 512MB 的地址空间。
    *   `ldr r0, =TblBase`:  加载 MMU 页表基地址 `TblBase` (即 `MMUTable` 的地址) 到 `r0`.
    *   `add r0, r0, #0x800`:  ==`0x800` 字节偏移 = 2048 字节 / 4 （bytes/entry） = 512 条目。这可能是为了 **跳过 MMU 表的前 512 个条目== (0x00000000 - 0x1fffffff)**,  从第 513 个条目开始设置。  **代码注释和这段代码本身似乎有矛盾，代码注释说映射 0x20000000 到 0x00000000，但是代码实现中，是跳过了 MMU 表的前 512 条目，从 0x20000000 对应的条目开始设置的。更可能是代码注释不准确，或者代码逻辑一开始是为了映射 0x20000000 -> 0x00000000，但后来改成了映射 0x20000000 之后的地址，但注释没有更新。**
    *   `ldr r2, =0x0c02`:  加载 MMU Section Descriptor 属性值 `0x0c02` (Non-Cacheable Data, Write-Bufferable) 到 `r2`.
    *   `mmu_loop:` 循环:
        *   `str r2, [r0]`:  将 `r2` 中的 MMU 条目属性值 **写入 MMU 页表 `MMUTable` 的当前地址 `[r0]`**.
        *   `add r0, r0, #0x4`:  `r0` 指针递增 4 字节，==指向下一个 MMU 条目位置。==
        *   `add r2, r2, #0x100000`: `r2` 的值递增 0x100000。  **这部分代码看着有疑问!  MMU Section Descriptor 里面的属性编码部分，不应该随着内存地址变化而变化，`0x0c02` 应该是固定的属性值才对。  这里 `add r2, r2, #0x100000`  是错误的，它会修改 MMU 属性值，导致后续的 MMU 条目属性设置错误。  正确的做法应该是 r2 的值保持 `0x0c02` 不变。 这很可能是代码错误。**
        *   `subs r3, r3, #1`:  循环计数器 `r3` 减 1.
        *   `bge mmu_loop`:  如果 `r3` 大于等于 0，则跳转回 `mmu_loop` 标签，继续循环。  循环 512 次后结束。

    **正确的代码应该是 `ldr r2, =0x0c02`  在 `mmu_loop` 循环外部，且循环内部不应该有 `add r2, r2, #0x100000`。**

4.  **设置不同模式下的栈指针 (SP/R13):**
    *   代码分别切换到 IRQ 模式 (0x12), Supervisor 模式 (0x13), Abort 模式 (0x17), System 模式 (0x1F)  通过修改 CPSR 寄存器的模式位。
    *   在每个模式下，加载对应的栈地址 (如 `IRQ_stack`, `SPV_stack`, `Abort_stack`, `SYS_stack`, 这些栈地址符号在前面用 `.set` 定义，最终链接器会替换为实际的栈地址) 到寄存器 `r13` (SP - Stack Pointer)。  ==**为不同的异常模式设置独立的栈空间，防止栈溢出互相影响。**==

5.  **启用 MMU 和 Cache:**
    *   `ldr r0,=TblBase`:  加载 MMU 页表基地址 `TblBase` 到 `r0`.
    *   `orr r0, r0, #0x5B`:  将 `r0` 与 `0x5B` 进行按位或运算。  `0x5B = 0b01011011`.  这部分代码是在设置 MMU 页表基地址寄存器 (TTBR0 - Translation Table Base Register 0) 的一些属性。  `0x5B`  (二进制 `0b01011011`)  可能包含的属性 (需要查阅 ARM 架构文档):
        *   **Outer Cacheability**: `0x5B` 中可能包含了设置 Outer Cache 为 Write-Back, Write-Allocate (WBWA) 的位。 注释中也提到 "Outer-cacheable, WB"。
        *   **Shareability Domain**:  可能包含了设置 Shareability Domain 的位。

        *   与 `#0x5B` 按位或，**实际上是设置了 TTB0 寄存器的控制位，以及保持了页表基地址不变**.  具体位域含义请查阅 ARM 架构文档中 TTBR0 寄存器的描述。
    *   `mcr 15, 0, r0, c2, c0, 0`:  将修改后的 `r0` (包含页表基地址和控制位)  写入 CP15 寄存器 2 (TTBR0 - Translation Table Base Register 0)。 ==**设置了 MMU 使用的页表基地址。**==
    *   `mvn r0,#0`:  将 `r0` 设置为 -1 (所有位都为 1)。
    *   `mcr p15,0,r0,c3,c0,0`:  将 `r0` 的值写入 CP15 寄存器 3 (DACR - Domain Access Control Register)。  域访问控制寄存器，设置为 -1 (所有域都为 Manager 权限)，**允许所有域的访问** (在 Domain-based 内存保护中，通常需要更精细的域权限控制)。

    *   `ldr r0,=0b01000000000101`:  加载立即数 `0b01000000000101` (十进制 4101) 到 `r0`.
    *   `mcr p15,0,r0,c1,c0,0`: 将 `r0` 的值写入 CP15 寄存器 1 (SCTRL - System Control Register)。 这部分代码是 **启用 MMU 和 Cache**。  解码 `0b01000000000101`:
        *   Bit 0: **M (MMU Enable) = 1**: 启用 MMU。
        *   Bit 2: **C (Data Cache Enable) = 1**: 启用 Data Cache。
        *   Bit 12: **I (Instruction Cache Enable) = 1**: 启用 Instruction Cache。
        *   其他位 (Bit 1, Bits 3-11, Bits 13-31) 为 0 或保留位，具体含义要查阅架构文档。  `0b01000000000101`  主要就是设置了 ==**启用 Instruction Cache, Data Cache, 和 MMU**。==
    *   `dsb`:  Data Synchronization Barrier.  **确保在 MMU 和 Cache 启用之后，内存系统操作的顺序性，防止数据访问顺序错乱。**  在 MMU 和 Cache 配置更改后使用 `dsb` 非常重要。
    *   `isb`:  Instruction Synchronization Barrier.  **刷新指令流水线，确保 MMU 和 Cache 的启用立即对后续指令取指生效。**  在 MMU 和 Cache 配置更改后使用 `isb` 也非常重要。

6.  **跳转到 `main` 函数:**
    *   `bl main`:  Branch with Link to `main` 函数。 **跳转到 C 代码的 `main` 函数入口，启动 C 语言编写的应用程序的主体部分。  至此，启动代码完成任务，控制权交给应用层代码。**

7.  `.Ldone: b .Ldone`:  无限循环。  万一 `main` 函数返回 (正常情况下，嵌入式系统 `main` 不应该返回，而是在一个无限循环中运行)，则程序会进入这个无限循环，防止程序跑飞。

**总结:**

这段汇编代码是典型的 ARM 启动代码，它的主要步骤是：

1.  **配置向量表基地址 (VBAR).**
2.  **初始化 MMU 页表 `MMUTable`，定义内存区域的映射和属性 (权限、缓存策略).**
3.  **设置不同异常模式的栈指针.**
4.  **设置 MMU 页表基地址寄存器 (TTBR0) 和域访问控制寄存器 (DACR).**
5.  **启用 MMU 和 Instruction/Data Cache.**
6.  **跳转到 C 代码的 `main` 函数，开始执行应用程序。**

**需要注意的代码疑点:**

*   **MMU 表中 DDR 区域的配置，注释说是 `(DDR Cacheable)`,  而实际代码  `0x15de6`  解码后 `C=b0 (Not Cacheable Data)`，这可能存在代码与注释不一致的问题，需要确认实际 DDR 区域是不是应该被配置为 Cacheable 的。**
*   **`mmu_loop` 循环内的 `add r2, r2, #0x100000` 指令是错误的， 它会修改 MMU 属性值，导致后续的 MMU 条目属性设置错误，应该移除。 正确代码应该保持 `r2` 的值 (属性值) 在整个循环中不变。**
*   代码尝试手动 "映射虚拟地址 0x20000000 到 0x00000000" 的注释， 和实际代码中 `add r0, r0, #0x800`  跳过 MMU 表前 512 条目的行为似乎不符。 需要仔细核对代码目的和注释是否一致.  更有可能是注释描述不准确, 实际代码是映射了 0x20000000 之后的 512MB 地址空间.

在实际使用这段代码时，**务必仔细检查 MMU 页表的配置是否符合硬件平台和系统需求，并修正代码中可能存在的错误 (如 `mmu_loop` 中的 `add r2, r2, #0x100000` 指令).  并根据 ARM 架构手册和硬件平台文档，验证 MMU Section Descriptor 属性编码 (`0x15de6`, `0xc02`, etc.) 的正确性。**  特别是 DDR 区域的缓存策略配置，需要根据具体的应用场景权衡性能和数据一致性。
### 以上代码如何实现将中断向量表映射到0地址
这段代码通过以下步骤将中断向量表映射到地址 `0x00000000` 或接近 `0x00000000` 的位置：

**1. 确保使用 VBAR 寄存器设置向量表基地址：**

   ```assembly
   /* Set V=0 in CP15 SCTRL register - for VBAR to point to vector */
   	mrc p15, 0, r0, c1, c0, 0	@ Read CP15 SCTRL Register
   	bic r0, #0x2000				@ CR_V : 1<< 13, V(bit[13]) = 0
   	mcr p15, 0, r0, c1, c0, 0	@ Write CP15 SCTRL Register
   ```

   *   `mrc p15, 0, r0, c1, c0, 0`:  读取 CP15 协处理器的系统控制寄存器 (SCTRL - System Control Register, 寄存器号 c1) 的值到寄存器 `r0`。
   *   `bic r0, #0x2000`:  清除 `r0` 寄存器中的位 13。在 ARM 架构的一些处理器 (包括 Zynq-7000 使用的 Cortex-A9)，SCTRL 寄存器的 **位 13 是 V 位 (Vectors bit)**。当 **V=0** 时，**异常向量表的基地址由 VBAR 寄存器 (Vector Base Address Register, CP15 寄存器 c12) 决定**。当 V=1 时，向量表基地址会被固定到一个预设地址 (通常是 0xFFFF0000 或 0x0，取决于处理器配置，但对于要映射到 0 的情况，需要 V=0 和使用 VBAR)。
   *   `mcr p15, 0, r0, c1, c0, 0`: 将修改后的 `r0` 值写回 CP15 的系统控制寄存器。 **通过将 V 位清零，确保了向量表的基地址将由 VBAR 寄存器来设置**。

**2. 设置 VBAR 寄存器指向 `_vector_table` 的地址：**

   ```assembly
   /* set VBAR to the _vector_table address in linker script*/
   	ldr	r0, =vector_base
   	mcr	p15, 0, r0, c12, c0, 0
   ```

   *   `ldr r0, =vector_base`:  **关键步骤！** 这条指令将 **`vector_base` 符号的地址** 加载到寄存器 `r0` 中。  `vector_base` 符号在代码前面通过 `.set vector_base, _vector_table` 定义，并且 `_vector_table` 是一个 `.global _vector_table` 声明的全局符号。 **`_vector_table` 这个符号的地址，需要通过链接脚本来控制其最终的内存位置。**  通常，在链接脚本中，`.vector_table` 段会被放置在地址 `0x00000000` 或非常接近 `0x00000000` 的低地址区域。  **`=` 符号在这里非常重要，表示加载的是 `vector_base` 的 *地址*，而不是 `vector_base` 的值。**
   *   `mcr p15, 0, r0, c12, c0, 0`:  将寄存器 `r0` 中的值 (也就是 `_vector_table` 的地址) 写入 CP15 的 **向量基地址寄存器 (VBAR, 寄存器号 c12)**。 **这步操作将 VBAR 寄存器设置为 `_vector_table` 的内存地址**。

**关键在于链接脚本和 `.vector_table` 段的放置：**

==为了使中断向量表真正映射到地址 `0x00000000`， **链接脚本必须配置成将 `.vector_table` 段 (或者包含 `_vector_table` 符号的段) 放置在内存地址 `0x00000000` 开始的区域** 。==

通常在链接脚本中，你会看到类似这样的段定义：

```linker script
SECTIONS {
    . = 0x00000000;  /* 将当前位置计数器设置为 0x00000000 */
    .vector_table : {  /* 定义 .vector_table 段 */
        *(.vector_table) /* 将所有输入文件中 .vector_table 段的内容放在这里 */
        _vector_table = .; /* 定义 _vector_table 符号为当前位置（即 0x00000000） */
    } > mem_region /* 指定将 .vector_table 段放置在 'mem_region' 内存区域，mem_region 需要是地址 0 开始的内存区域 */

    /* ... 其他段的定义 ... */
}
```

**总结：**

==这段汇编代码本身负责 **设置 VBAR 寄存器指向 `_vector_table` 符号的地址**。  **要实现将中断向量表映射到地址 `0x00000000`，还需要配合正确的链接脚本：**==

1.  **链接脚本需要将包含中断向量定义的段 (例如 `.vector_table` 段)  放置在地址 `0x00000000` 开始的内存区域。**
2.  **链接脚本需要在 `.vector_table` 段的起始位置定义全局符号 `_vector_table`，以便汇编代码可以引用到这个地址。**

当汇编代码执行到 `ldr r0, =vector_base` 和 `mcr p15, 0, r0, c12, c0, 0` 指令时，  VBAR 寄存器就会被设置为 `_vector_table` 在内存中的实际地址，如果链接脚本正确配置，这个地址就将是 `0x00000000` 或非常接近 `0x00000000` 的低地址。之后，当发生异常或中断时，处理器就会根据 VBAR 寄存器指向的地址，去地址 `0x00000000` (或接近 0 的地址)  处取出对应的异常向量进行处理。
