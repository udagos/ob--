#  **主机开发环境搭建**



### 搭建过程详解

#### 1. 基础操作系统环境

*   **操作**:
    1.  安装 **VirtualBox** 虚拟机软件。
    2.  在 VirtualBox 中安装 **Ubuntu 14.04 32位** 操作系统。
    3.  安装虚拟机增强功能并设置共享目录 (`/mnt/f`)。
*   **原因**:
    *   **隔离与标准化**: 使用虚拟机（VM）可以创建一个干净、独立且标准化的开发环境，避免与主机本身的操作系统（如 Windows）发生冲突。如果环境出现问题，可以轻松地恢复快照或重建，而不会影响主机。
    *   **Linux 生态**: 嵌入式 Linux 的开发和编译工具链在 Linux 操作系统上支持最好、运行最稳定，因此选择 Ubuntu 作为开发环境。
    *   **文件共享**: 设置共享目录是为了方便地在主机（如 Windows）和虚拟机（Ubuntu）之间传输文件，例如下载好的开发包和源代码。

#### 2. 安装 SDK 和必需的开发组件

*   **操作**:
    1.  **安装 Xilinx SDK**:
        *   `sudo chmod 777 /opt`: 修改 `/opt` 目录的权限。
        *   运行 `xsetup` 安装程序。
    2.  **安装其他系统组件**:
        *   `sudo apt-get install vim`: 安装 Vim 编辑器。
        *   `sudo apt-get install subversion`: 安装 Subversion (SVN) 版本控制工具。
        *   `sudo apt-get install ncurses-dev`: 安装 ncurses 开发库。
*   **原因**:
    *   **解决 SDK 安装权限**: Xilinx SDK 默认安装在 `/opt` 目录下，但该目录通常需要管理员权限才能写入。`chmod 777 /opt` 命令简单粗暴地赋予了所有用户读、写、执行的权限，以确保安装程序能顺利进行。
    *   **获取交叉编译器**: 安装 Xilinx SDK 的核心目的是获取之前提到的**交叉编译工具链**。
    *   **准备辅助工具**:
        *   `vim`: 一个功能强大的命令行文本编辑器，用于查看和修改代码及配置文件。
        *   `subversion`: 一个版本控制系统，用于管理项目代码（类似于 Git）。
        *   `ncurses-dev`: 这是**非常关键**的一个库。后续在配置 Linux 内核时，会用到一个名为 `menuconfig` 的工具，它提供了一个基于文本的图形化菜单界面。这个界面依赖于 `ncurses` 库来绘制。如果没有安装这个开发库，`make menuconfig` 命令将会失败。

#### 3. 准备和展开源代码

*   **操作**:
    1.  `mkdir /home/zzy/workspace/zynq_base_14_7`: 创建一个专门的工作空间目录。
    2.  `tar xzvf ...`: 使用 `tar` 命令将下载好的 U-Boot 和 Linux 的 `.tar.gz` 源码压缩包解压到这个工作空间目录中。
*   **原因**:
    *   **项目组织**: 将所有相关的源代码放在一个统一的工作空间目录下，便于管理和查找，是一个良好的开发习惯。
    *   **获取源码**: `tar` 是 Linux 系统下用于处理 `.tar.gz` 压缩包的标准工具。这个命令将压缩的源码文件解开，形成完整的、可以进行配置和编译的源代码目录树。

### 总结

“主机开发环境搭建”这一系列操作，本质上是一个**“三步走”**的准备过程：
1.  **搭建一个基础的 Linux 系统平台** (通过虚拟机)。
2.  **在这个平台上安装所有“兵器”** (交叉编译器 SDK 和其他辅助开发工具)。
3.  **将要加工的“原材料”准备好** (解压 U-Boot 和 Linux 源代码)。

完成这些步骤后，开发者就有了一个功能完备的“工厂”，可以开始进行后续的配置和编译工作了。
# 开发包选择

这部分的核心是为 ZedBoard 开发板选择一套可靠、匹配且持续维护的软件开发工具和源代码。

### 选择过程和决策逻辑

1.  **初步尝试与遇到的问题**:
    *   开发者首先访问了 ZedBoard 的官方网站 (`zedboard.org`)，但发现该网站主要提供硬件资料，**没有提供完整的软件开发包**。
    *   接着，他们发现开发板 SD 卡中的示例文件是由 Digilent (ZedBoard 的制造商) 提供的，并从 Digilent 网站下载了一个开箱即用 (Out-of-Box) 的设计包。但关键问题是，这个包**已经不再维护**。

2.  **最终决策**:
    *   **决策**: 放弃不再维护的 Digilent 开发包，转而采用 **Xilinx 官方**提供的开发包。
    *   **原因**:
        *   **权威性与可靠性**: Xilinx 是 Zynq 芯片的原厂商，他们官方维护的 Linux 源码包（`linux-xlnx`）是针对其芯片适配最完善、最权威的版本。
        *   **持续维护**: 与已经停止更新的 Digilent 包不同，Xilinx 官方会持续发布新版本、修复 bug，这对于项目的长期稳定至关重要。

### 选择的具体软件包

在确定了“跟随 Xilinx 官方”的路线后，开发者选择了以下具体的版本：

#### 1. 软件开发工具 (SDK)

*   **选择**: **Vivado and SDK 2013.4**
*   **下载内容**: `All OS Vivado and SDK Full Installer`
*   **原因**:
    *   这是在项目开发**当时最新的版本**。
    *   对于构建 Linux 系统而言，这个庞大的安装包中最重要的部分是其包含的**交叉编译工具链** (`arm-xilinx-linux-gnueabi-`)。这是后续编译 U-Boot 和 Linux 内核所必需的。

#### 2. U-Boot 和 Linux 内核源码

*   **选择**:
    *   **U-Boot**: `u-boot-xlnx-xilinx-v14.7.tar.gz`
    *   **Linux 内核**: `linux-xlnx-xilinx-v14.7.tar.gz`
*   **下载来源**: Xilinx 在 GitHub 上的官方代码仓库 (`Xilinx/u-boot-xlnx` 和 `Xilinx/linux-xlnx`)。
*   **原因**:
    *   **版本匹配**: 选择了 `xilinx-v14.7` 这个带标签的特定版本。在 Xilinx 的开发体系中，工具（Vivado SDK）和源码（U-Boot, Linux）的版本通常是相互关联的。选择一个明确的发布版本（release tag）可以确保工具链和源代码之间有良好的兼容性，避免因版本不匹配导致的各种奇怪问题。
    *   **稳定性**: `v14.7` 是当时 Xilinx Wiki 上记录的最后一个稳定发布版本，从稳定版入手是项目开发的稳妥选择。
    *   **格式注意**: 文档特别提到，要下载 `.tar.gz` 格式的源码包，因为 `.zip` 格式在解压时可能会出现问题（通常是文件权限或符号链接丢失的问题）。

### 总结

开发包选择的整个过程体现了一个清晰的思路：**优先选择芯片原厂 (Xilinx) 提供的、有持续维护的、版本明确且相互匹配的官方软件开发包**，而不是板卡制造商 (Digilent) 提供的可能已过时的便利包。这个决策为项目的稳定性和后续的技术支持奠定了坚实的基础。


# 内核相关代码 （包括 U-Boot、Linux 内核和设备树）的编译过程

这个过程的目标是为 ZedBoard 开发板创建三个核心的软件组件，以便启动一个嵌入式 Linux 系统。

---

### 1. U-Boot 编译 (引导加载程序)

U-Boot 是一个开源的引导加载程序，它的主要任务是在系统上电后初始化硬件（如内存、时钟），然后从存储设备（如 SD 卡）中加载 Linux 内核和设备树到内存中，最后启动内核。

#### 编译过程：

1.  **`make ARCH=arm zynq_zed_config`**
    *   **过程**: 此命令为 U-Boot 源码配置目标平台。
    *   **解释**: 它会读取 `configs/zynq_zed_config` 这个预设的配置文件，并根据它生成一个 `.config` 文件。这个文件包含了为 Zynq ZedBoard 量身定制的所有编译选项，比如启用哪些驱动、设置哪些硬件参数等。
    *   **原因**: U-Boot 支持成百上千种硬件。在编译前，必须先明确地告诉编译系统“我是要为 Zynq ZedBoard 这块板子编译”，这样才能生成与之兼容的程序。

2.  **`make ARCH=arm`**
    *   **过程**: 这是实际的编译命令。
    *   **解释**: `make` 工具会读取上一步生成的 `.config` 文件，然后编译所有必需的 C 语言和汇编源代码，最终将它们链接成可执行的 U-Boot 程序。文档提到，这会生成 `u-boot.elf` (用于调试和集成) 和 `u-boot.bin` (原始二进制文件) 两个文件。
    *   **原因**: 这是将源代码转化为可在目标硬件上运行的程序的关键一步。

3.  **`export PATH=` pwd `:$PATH` (在 `tools` 目录下执行)**
    *   **过程**: 将 U-Boot 源码中的 `tools` 目录临时添加到系统的 `PATH` 环境变量中。
    *   **解释**: U-Boot 的 `tools` 目录里包含一些在主机上运行的辅助工具，其中最重要的就是 `mkimage`。这个工具在后续步骤中需要用来给 Linux 内核和 ramdisk 添加一个 U-Boot 能识别的“头部信息”。
    *   **原因**: 为了在后续步骤中能方便地直接调用 `mkimage` 命令，而不需要输入它的完整路径。

---

### 2. Linux 内核编译

这是操作系统的核心部分，负责管理硬件资源、调度进程等。

#### 编译过程：

1.  **`make ARCH=arm xilinx_zynq_defconfig`**
    *   **过程**: 为 Linux 内核加载一个默认的配置文件。
    *   **解释**: 和 U-Boot 类似，这个命令会根据 Xilinx 官方为 Zynq 平台提供的默认配置 (`xilinx_zynq_defconfig`) 生成一个 `.config` 文件。这个默认配置确保了所有在 Zynq 上运行 Linux 所必需的核心驱动和功能都已被启用。
    *   **原因**: 从一个官方验证过的默认配置开始，是确保能成功编译并启动一个可用内核的最可靠方法。

2.  **`make ARCH=arm menuconfig`**
    *   **过程**: 启动一个基于文本的图形化菜单，用于自定义内核配置。
    *   **解释**: 开发者可以在这个菜单中对默认配置进行修改，比如添加对特定硬件的支持，或者裁剪掉不需要的功能以减小内核体积。
    *   **原因**: 提供一个定制内核的入口。虽然默认配置能用，但实际项目往往需要根据具体需求进行调整。

3.  **`make ARCH=arm UIMAGE_LOADADDR=0x8000 uImage`**
    *   **过程**: 编译内核，并生成一个 U-Boot 专用的 `uImage` 格式的内核镜像。
    *   **解释**:
        *   `uImage`: 这不是一个普通的内核文件，而是一个在原始内核（`zImage`）前面加上了 64 字节“头部”的特殊格式文件。U-Boot 会读取这个头部，以获取内核的大小、加载地址、入口地址等信息。
        *   `UIMAGE_LOADADDR=0x8000`: 这个参数至关重要，它告诉 `mkimage` 工具在生成头部时，应指定内核被加载到内存的地址是 `0x00008000`。
    *   **原因**: U-Boot 只能识别和加载带有特定头部的 `uImage` 格式的内核。设置正确的加载地址可以确保 U-Boot 将内核放置在预期的内存位置，否则系统将无法启动。

---

### 3. Device Tree (设备树) 编译

设备树是一个描述硬件信息的数据结构。Linux 内核在启动时会读取它，以了解板子上到底有哪些硬件设备以及它们是如何连接和配置的。

#### 编译过程：

1.  **`make ARCH=arm zynq-zed.dtb`**
    *   **过程**: 将人类可读的设备树源文件 (`.dts`) 编译成内核可用的二进制文件 (`.dtb`)。
    *   **解释**: `zynq-zed.dts` 是一个文本文件，用特定的语法描述了 ZedBoard 上的各种硬件资源。此命令调用设备树编译器 (`dtc`) 将其转换为紧凑的二进制格式。
    *   **原因**: 内核在启动的早期阶段就需要了解硬件布局，但此时它还无法运行复杂的代码去探测硬件。因此，它依赖于 U-Boot 预先加载到内存中的这个二进制 `.dtb` 文件，直接从中读取硬件信息。这种方式将硬件描述与内核代码分离，使得同一个内核镜像可以适配不同的硬件板卡（只需更换 `.dtb` 文件）。

2.  **修改 `zynq-zed.dts` 文件**
    *   **过程**: 文档提到，开发者发现默认的 `.dts` 文件中以太网 PHY 芯片的地址是错的（写的是 7，实际是 0），并手动进行了修正。
    *   **原因**: 这是一个非常典型的嵌入式开发场景。硬件的实际情况可能与官方提供的默认配置文件有细微差别。设备树的存在使得修复这类问题变得非常简单：只需修改文本描述文件并重新编译小小的 `.dtb` 文件即可，无需重新编译整个庞大的 Linux 内核。
# Ramdisk 的制作和修改过程。
好的，我将根据文档内容，为您详细解释 Ramdisk 的制作和修改过程。

**Ramdisk**（内存盘）在这里指的是一个被加载到内存（RAM）中运行的根文件系统（Root Filesystem）。当 Linux 内核启动后，它会挂载这个内存中的文件系统作为其根目录 (`/`)，从而可以访问到 `/bin`, `/etc`, `/lib` 等目录下的基本程序和配置文件，并完成系统的初始化。

---

### 一、制作一个可被 U-Boot 加载的初始 Ramdisk

这个过程的目标是将一个标准的 Ramdisk 文件系统镜像，转换成 U-Boot 能够识别和加载的格式。

#### 过程：

1.  **下载基础镜像**:
    *   `http://www.wiki.xilinx.com/file/view/arm_ramdisk.image.gz/419243558/arm_ramdisk.image.gz`
    *   **解释**: 首先从 Xilinx 官方 Wiki 下载一个预先制作好的 Ramdisk 镜像文件。这个文件 `arm_ramdisk.image.gz` 本质上是一个使用 `gzip` 压缩过的文件系统存档。

2.  **添加 U-Boot 头部**:
    *   **命令**: `mkimage -A arm -T ramdisk -C gzip -d arm_ramdisk.image.gz uramdisk.image.gz`
    *   **解释**:
        *   `mkimage`: 这是 U-Boot 工具集中的一个关键工具，专门用来给各种镜像文件（内核、Ramdisk 等）添加 U-Boot 可识别的头部。
        *   `-A arm`: 指定架构为 ARM。
        *   `-T ramdisk`: 指定镜像类型为 Ramdisk。
        *   `-C gzip`: 指定镜像的压缩类型为 gzip。
        *   `-d arm_ramdisk.image.gz`: 指定输入的原始数据文件。
        *   `uramdisk.image.gz`: 指定输出的文件名。
    *   **原因**: U-Boot 不会直接加载一个普通的压缩文件。它需要读取一个 64 字节的头部信息来了解这个镜像的类型、架构、大小、压缩方式等元数据。`mkimage` 的作用就是生成并添加这个头部，得到最终的 `uramdisk.image.gz` 文件，这个文件才能被 U-Boot 正确加载。

---

### 二、修改 Ramdisk 的内容

在实际开发中，官方提供的基础 Ramdisk 往往不能满足项目需求（比如需要添加自己的应用程序、修改配置文件等）。因此，需要先解压、修改，然后再重新打包。

#### 过程：

1.  **创建工作目录并解压**:
    *   **命令**:
        ```bash
        mkdir current_ramdiskfs
        cd ./current_ramdiskfs
        gunzip -c ../rootfs.cpio.gz | cpio -idmv
        ```
    *   **解释**:
        *   `mkdir` 和 `cd` 创建并进入一个新的工作目录。
        *   `gunzip -c`: 解压 `rootfs.cpio.gz` 文件，并将内容输出到标准输出。
        *   `|`: 管道符，将 `gunzip` 的输出传递给 `cpio` 命令。
        *   `cpio -idmv`: `cpio` 是一个文件归档工具。这里的参数意味着**提取** (`-i`) 归档内容，根据需要**创建目录** (`-d`)，**保留文件修改时间** (`-m`)，并显示过程 (`-v`)。
    *   **原因**: 这个步骤将压缩的 Ramdisk 文件系统完整地解开，变成了一个可以在主机上直接访问和修改的普通目录 (`current_ramdiskfs`)。

2.  **修改文件系统内容**:
    *   **过程**: 在 `current_ramdiskfs` 目录中，开发者可以像操作普通文件一样，添加、删除或编辑任何文件和目录，以定制自己的文件系统。

3.  **重新打包并压缩**:
    *   **命令**: `find . | cpio -H newc -o | gzip -9 > ../rootfs.cpio.gz`
    *   **解释**:
        *   `find .`: 列出当前目录下的所有文件和目录。
        *   `| cpio -H newc -o`: 将 `find` 列出的文件列表打包成一个 `cpio` 归档。`-o` 表示创建归档，`-H newc` 指定了归档的格式。
        *   `| gzip -9`: 将 `cpio` 生成的归档内容通过管道传递给 `gzip`，并使用最高压缩等级 (`-9`) 进行压缩，最终生成新的 `rootfs.cpio.gz` 文件。
    *   **原因**: 将修改后的目录和文件重新制作成一个单一的、压缩过的 Ramdisk 镜像文件。

4.  **为新的 Ramdisk 添加 U-Boot 头部**:
    *   **命令**: `mkimage -A arm -T ramdisk -C gzip -d rootfs.cpio.gz uramdisk20140116.image.gz`
    *   **解释**: 这个步骤和第一部分完全相同，目的依然是为新制作的、经过修改的 Ramdisk 镜像添加 U-Boot 能识别的头部。
    *   **原因**: 任何要被 U-Boot 加载的 Ramdisk 都必须带有这个头部，无论是原始的还是修改过的。

至此，一个包含了自定义内容的、可以被 U-Boot 正确加载的 Ramdisk 镜像 (`uramdisk20140116.image.gz`) 就制作完成了。
