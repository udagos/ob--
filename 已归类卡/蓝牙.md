# 介绍
好的，蓝牙连接建立是一个相对复杂但又非常核心的过程，它涉及到多个步骤和协议。作为嵌入式系统专家，我来为您详细解释一下蓝牙连接建立的过程，力求清晰、准确、并且易于理解。为了更全面，我会尽可能涵盖经典蓝牙 (Bluetooth Classic) 和低功耗蓝牙 (Bluetooth Low Energy, BLE) 的连接建立流程，并指出关键差异。

**蓝牙连接建立的总览框架 (通用步骤):**

无论经典蓝牙还是 BLE，连接建立过程都大致可以分解为以下几个核心阶段：

1. **设备发现 (Device Discovery):**  一方设备扫描周围的蓝牙设备，找到希望连接的目标设备。
2. **设备选择 (Device Selection):** 在发现的设备列表中，用户或应用选择要连接的目标设备。
3. **连接请求 (Connection Request):** 发起连接请求，尝试与目标设备建立物理连接。
4. **连接接受 (Connection Acceptance):** 目标设备接受连接请求，建立物理连接。
5. **配对/绑定 (Pairing/Bonding，可选但常用):**  为了安全性和便捷性，设备可能进行配对或绑定，交换密钥，建立信任关系。 (注意：并非所有连接都需要配对，例如 BLE 的广播应用)
6. **服务发现 (Service Discovery):**  连接建立后，客户端设备发现服务端设备提供的服务和特性，以便后续的数据交互。
7. **连接维护与数据传输 (Connection Maintenance & Data Transfer):**  连接保持，并根据应用场景进行数据交换。

接下来，我们分别针对 **经典蓝牙 (Bluetooth Classic - BR/EDR)** 和 **低功耗蓝牙 (Bluetooth Low Energy - BLE)**，详细展开每个阶段的流程和关键技术点。

**一、经典蓝牙 (Bluetooth Classic - BR/EDR) 连接建立过程:**

经典蓝牙常用于音频传输、文件传输等场景，采用面向连接的 ACL (Asynchronous Connection-Less) 链路。

1. **设备发现 (Inquiry Procedure):**
   * **查询扫描 (Inquiry Scan):** 想要发起连接的设备 (通常是主设备，Master) 进入 Inquiry Scan 状态，周期性地在蓝牙频段发送 **Inquiry 请求** 数据包。
   * **查询响应 (Inquiry Response):** 周围处于可被发现状态的蓝牙设备 (通常是从设备，Slave) 接收到 Inquiry 请求后，会发送 **Inquiry Response** 数据包作为回应。  Inquiry Response 中包含设备的蓝牙地址 (BD_ADDR)、时钟偏移量 (Clock Offset) 和 设备类型 (Class of Device, CoD) 等信息。
   * **页面扫描 (Page Scan):**  主设备接收到 Inquiry Response 后，如果确定要连接某个设备，则会进入 Page Scan 状态，向目标设备的蓝牙地址发送 **Page 请求** 数据包，尝试建立连接。

2. **设备选择 (Device Selection):**
   * 用户或应用程序会看到扫描到的设备列表 (基于 Inquiry Response 的信息)。
   * 用户选择要连接的设备。

3. **连接请求 (Page Procedure - Page Request):**
   * 主设备向选定的目标设备 (从设备) 的蓝牙地址发送 **Page 请求** 数据包。Page 请求中包含主设备的蓝牙地址等信息。
   * Page 请求的目标地址就是之前 Inquiry Response 中获取到的从设备地址。

4. **连接接受 (Page Procedure - Page Response & Connection Complete):**
   * 从设备收到 Page 请求后，如果接受连接，会发送 **Page Response** 数据包作为回应。
   * 主设备收到 Page Response 后，认为连接建立成功，会进入 **Connection 状态**，并发送 **Connection Complete** 事件给上层协议栈。
   * 此时，物理链路 ACL 连接建立完成。

5. **配对/绑定 (Pairing/Bonding - Security Manager Protocol, SMP):**
   * **配对 (Pairing):**  为了安全通信，设备通常会进行配对。配对过程通过 **Security Manager Protocol (SMP)** 协议完成。
     * **配对请求 (Pairing Request) / 响应 (Pairing Response):** 主从设备协商配对能力 (例如是否支持密钥交换、加密类型等)。
     * **密钥生成和交换:**  根据配对方式 (例如 Legacy Pairing, Secure Simple Pairing - SSP)，设备可能需要用户输入 PIN 码或进行数字比较、Just Works 等操作，完成加密密钥 (Link Key) 的生成和交换。
     * **链路加密 (Link Encryption):** 配对成功后，可以使用生成的 Link Key 对后续的 ACL 数据链路进行加密。
   * **绑定 (Bonding):**  如果设备选择绑定，会将配对过程中生成的 Link Key **持久化存储**。下次连接时，可以直接使用已保存的 Link Key 进行身份验证和加密，无需重复配对过程，更加方便快捷。

6. **服务发现 (Service Discovery Protocol, SDP):**
   * 连接建立和配对 (如果需要) 完成后，客户端设备 (通常是主设备) 会使用 **Service Discovery Protocol (SDP)** 来查询服务端设备 (通常是从设备) 提供的服务。
   * **SDP 请求 / 响应:**  客户端发送 SDP 请求 (例如 Service Search Request, Service Attribute Request 等) 到服务端。服务端根据请求，返回 SDP 响应，其中包含服务记录 (Service Record)，描述了服务端提供的服务类型、UUID、协议栈、端口号等信息。
   * 客户端根据 SDP 响应的信息，了解服务端支持哪些服务，并选择需要的服务进行后续通信。例如，发现服务端支持音频传输服务 (A2DP profile)。

7. **连接维护与数据传输:**
   * 连接建立后，设备之间可以开始进行数据传输。
   * 经典蓝牙通常使用 L2CAP (Logical Link Control and Adaptation Protocol) 层进行数据包的封装和分段重组。
   * 上层应用可以使用不同的蓝牙 Profile (例如 A2DP, AVRCP, HSP, HFP, OPP, FTP 等) 进行 specific 功能的数据交互，例如音频流传输、远程控制、文件传输等。

**二、低功耗蓝牙 (Bluetooth Low Energy - BLE) 连接建立过程:**

BLE 主要用于低功耗、间歇性数据传输的场景，例如物联网设备、可穿戴设备等。  BLE 使用面向连接的连接 (connection) 和 无连接的广播 (broadcasting) 两种通信模式。 这里我们关注连接建立过程。

1. **设备发现 (Advertising & Scanning):**
   * **广播 (Advertising):**  希望被发现的 BLE 设备 (通常是 Peripheral 设备，外围设备)  周期性地发送 **Advertising 数据包**。 Advertising 数据包在特定的广播信道 (Advertising Channels) 上发送。 Advertising 数据包中包含设备地址、设备名称、广播数据 (Advertising Data) 和 扫描响应数据请求指示 (Scan Request Indication) 等信息。
   * **扫描 (Scanning):**  希望发起连接的 BLE 设备 (通常是 Central 设备，中央设备)  进入 Scanning 状态，监听广播信道，接收 Advertising 数据包。
   * **扫描响应 (Scan Response，可选):**  Peripheral 设备可以响应 Central 设备的 **Scan Request** 数据包，发送 **Scan Response** 数据包，提供更多的设备信息。

2. **设备选择 (Device Selection):**
   * Central 设备接收到多个 Peripheral 设备的 Advertising 数据包后，会解析广播数据，提取设备名称、 服务 UUID (Service UUIDs) 等信息。
   * 用户或应用程序会看到扫描到的设备列表 (基于 Advertising 数据中的信息)。
   * 用户选择要连接的 Peripheral 设备。

3. **连接请求 (Connection Request):**
   * Central 设备向选定的 Peripheral 设备发送 **Connection Request** 数据包。Connection Request 数据包包含了连接参数，例如连接间隔 (Connection Interval)、从机延迟 (Slave Latency)、超时时间 (Supervision Timeout) 等，以及 Central 设备的地址。

4. **连接接受 (Connection Acceptance & Connection Complete):**
   * Peripheral 设备收到 Connection Request 后，如果接受连接，会回复 **连接响应** (通常是直接开始接收数据而没有显式的响应数据包，在链路层层面是 ACK 机制)。
   * 连接建立后，Central 设备会发送 **Connection Complete** 事件给上层协议栈。
   *  BLE 连接建立后，物理链路 BLE 连接建立完成。

5. **配对/绑定 (Pairing/Bonding - BLE Security Manager, SM):**
   * BLE 的配对和绑定过程也由 **Security Manager (SM)** 层处理，类似于经典蓝牙的 SMP。
   * **配对请求 (Pairing Request) / 响应 (Pairing Response):**  Central 和 Peripheral 设备交换配对能力信息。
   * **密钥交换:**  BLE 支持不同的配对方法，例如 Just Works, Passkey Entry, Out-of-Band (OOB) 等，根据不同的方法进行密钥生成和交换，生成加密密钥 (Long Term Key - LTK, Short Term Key - STK 等)。
   * **链路加密 (Link Encryption):**  配对成功后，链路可以使用加密密钥进行加密。
   * **绑定 (Bonding):**  BLE 也支持绑定，持久化存储配对密钥 (例如 LTK)。  BLE 的绑定信息通常包括 LTK, 长期密钥地址类型 (Long Term Key Address Type),  连接间隔 (Connection Interval) 等。

6. **服务发现 (GATT Service Discovery):**
   * BLE 连接建立和配对 (如果需要) 完成后，客户端设备 (通常是 Central 设备)  使用 **Generic Attribute Profile (GATT)** 进行服务发现。
   * **GATT 服务发现流程:** Central 设备发送 GATT 服务发现请求 (例如 Discover All Primary Services Request) 到 Peripheral 设备。 Peripheral 设备回复 GATT 服务发现响应 (Discover All Primary Services Response)，列出其支持的 GATT 服务，包括服务 UUID、服务句柄 (Handle) 等。
   * Central 设备可以进一步发现服务中的 **Characteristic (特征值)** 和 **Descriptor (描述符)**，了解服务提供的具体数据和功能。

7. **连接维护与数据传输 (GATT Operations):**
   * BLE 连接建立后，数据传输通常通过 **GATT Profile** 进行。
   * **GATT 操作:**  Central 设备可以通过 GATT 操作 (例如 Read Characteristic Value, Write Characteristic Value, Notify, Indicate 等)  与 Peripheral 设备交换数据。
   * BLE 连接的维护 (Connection Parameter Update) 和数据传输都更加侧重于低功耗设计，例如使用较长的连接间隔，较低的发射功率等。

**经典蓝牙 vs. BLE 连接建立的主要差异总结:**

| 特性          | 经典蓝牙 (BR/EDR)                                  | 低功耗蓝牙 (BLE)                                     |
|---------------|----------------------------------------------------|------------------------------------------------------|
| 主要应用场景    | 音频传输、文件传输、较高数据速率                 | 低功耗数据传输、物联网、传感器、可穿戴                |
| 连接类型        | 面向连接的 ACL 链路                                  | 面向连接的连接，以及无连接的广播模式                   |
| 设备发现        | Inquiry/Page Scan, Inquiry/Page Response         | Advertising/Scanning, Scan Request/Response (可选)   |
| 服务发现        | 服务发现协议 SDP                                     | 通用属性 Profile GATT                                   |
| 配对协议        | Security Manager Protocol (SMP)                     | BLE Security Manager (SM)                               |
| 功耗          | 相对较高                                           | 非常低功耗                                             |
| 连接参数        | 较少可配置的连接参数                                 | 连接间隔、从机延迟、超时时间等可细致配置，优化功耗        |
| 数据速率        | 更高                                               | 相对较低，但足以满足物联网等应用                      |
| 广播模式        | 主要面向连接                                         | 广播是重要的通信模式，用于无连接数据发布             |
| 复杂性          | 协议栈相对复杂                                       | 协议栈相对简化，更易于嵌入式系统实现                   |

```
    E -- Scan Response --> A;
```
**总结:**

蓝牙连接建立过程是一个多步骤、多协议协作的过程，涉及到设备发现、连接请求、连接接受、配对/绑定、服务发现和数据传输等关键阶段。 理解经典蓝牙和 BLE 在这些阶段的具体流程和差异，对于嵌入式蓝牙开发和应用至关重要。 掌握这些知识，才能更好地进行蓝牙设备的开发、调试和问题排查。

**4. BLE 数据交换 (GATT Characteristic Read/Write)  (概念性描述):**

在服务和特征值发现之后，你就可以根据特征值的属性 (Properties) 进行数据读写操作了。  例如：

* **读取 Characteristic 值 (Read):**
    * 调用类似 `ble_gatt_read_characteristic_value(connection_handle, characteristic_handle, read_callback)` 的 API。
    * 提供一个读回调函数 `read_callback(status, value, value_len)` 来接收读取结果。
* **写入 Characteristic 值 (Write):**
    * 调用类似 `ble_gatt_write_characteristic_value(connection_handle, characteristic_handle, value, value_len, write_type, write_callback)` 的 API。
    * `write_type` 可以是请求响应模式 (With Response) 或 无响应模式 (Without Response)。
    * 提供一个写回调函数 `write_callback(status)` 来接收写入结果 (仅在请求响应模式下有回调)。
* **订阅 Notification 或 Indication (Notify/Indicate):**
    * 对于支持 Notify 或 Indicate 属性的 Characteristic，可以使能 Notification 或 Indication  (通常是通过写入 Client Characteristic Configuration Descriptor, CCCD)。
    * Peripheral 设备会在 Characteristic 值变化时，向 Central 设备发送 Notification 或 Indication 数据。
    * Central 设备需要注册一个接收 Notification/Indication 的回调函数 `notification_indication_callback(characteristic_handle, value, value_len)`。

**重要提示:**

* **平台和 SDK 差异:**  上述代码示例中的函数名、参数和回调函数只是 **示意性的**。 实际的蓝牙 API 会因你使用的平台 (操作系统、蓝牙芯片、蓝牙协议栈) 而 **有很大差异**。  请务必参考你所用平台的 **蓝牙 API 文档** 和 **示例代码**。
* **错误处理:**  实际蓝牙编程中，**错误处理至关重要**。  蓝牙 API 调用通常会返回状态码，你需要检查这些状态码，并根据错误情况进行处理 (例如，重试、断开连接、提示用户等)。  示例代码为了简化，省略了错误处理部分，实际应用中需要添加完善的错误处理机制。
* **异步编程:**  蓝牙操作通常是 **异步的**。 例如，发起扫描、连接、服务发现等操作后，结果不会立即返回，而是通过 **回调函数** (callbacks) 或 **事件** (events)  来通知应用程序操作完成或状态变化。  理解和掌握异步编程模型是蓝牙开发的关键。
* **功耗优化 (BLE):**  在 BLE 开发中，功耗优化是一个重要的考虑因素。 合理设置连接参数 (连接间隔、从机延迟、超时时间)、选择合适的广播和扫描模式、减少数据传输量等，可以有效降低功耗。

希望这些代码示例能帮助你更好地理解蓝牙连接建立过程的代码实现思路。为了进行实际的蓝牙开发，你需要选择合适的硬件平台和蓝牙 SDK，并认真阅读相关的 API 文档和示例代码。祝你蓝牙开发顺利！



# 总体安富莱
## 架构
从蓝牙架构上来说，因为蓝牙是应手机而生的，最初做出来就是为了解决手机连接的问题的。  
一种常见的架构就是HOST+CONTROLLER。
HOST就是指手机的芯片，CONTROLLER就是蓝牙芯片。HOST根据一个标准的协议HCI，去控制CONTROLLER芯片。这样做的好处就是更换HOST或者更换蓝牙芯片，对程序没有影响，完全可以兼容。  
  
第二种就是单颗芯片整体方案。  
例如我们的乐鑫ESP32就是这样啦，HOST和CONTROLLER在同一颗芯片上。不过ESP32也可以配置成工作在CONTROLLER，然后串口引出来，让别的MCU通过HCI控制它。当成第一种方法来使用。  
  
第三种就是非标准的HCI协议，这里不涉及。
